# The inner passes: what abp@ will check, and a proposal for Dinis

Source: `board/guidance/2026-11-18-inner-passes-and-security.md` (Dinis, 18 Nov about 15:05 and 15:10 UTC, recorded by conductor.b@; read in the repository, the session message only pointed to it). Nothing in the policy is changed here.

## What abp@ can do now, with no policy change (from the next wake)
- **A wake that skipped the passes is a finding:** each wake's commit or `status.json` must say the passes ran and what the post-review found ("clean" counts). abp@ reads the commit bodies and `status.json` each hour and lists agents whose wake says nothing about them.
- **Sub-agents inside a run:** the passes run as Sonnet sub-agents; only agents with `subagents: true` in their grant can start them. Those without (outreach, researcher, correspondent, accountant and others) cannot run the passes as written: abp@ lists them below for Dinis rather than granting sub-agents myself.

## Proposal, three steps (Dinis decides)
1. **Run-report field `passes`** (schema + `run-report --passes ran|skipped --findings "<text>"`): the run report says whether the opening conductor pass, the security pre-review, the post-review (AppSec when code changed) and the closing pass ran. `abp.mjs report` turns an empty field into a finding. No blocking.
2. **ABP text:** every ABP gets a short "Inner passes" section (generated, from `policies.json`): the five steps, restored at every compaction with the rules, so an agent after a compaction still knows to run them. For agents that write code, the AppSec list is added (injection, untrusted input, escaping, secrets, dependencies, CI tokens, SSRF and hosts, parsing, rate limits).
3. **Hook support (observe mode, logging only):** a `PreToolUse`/Stop check that a commit by an agent that writes code carries a line saying the AppSec post-review ran; missing is logged, never blocked. abp@ does not propose blocking this.

## Agents without sub-agents who would need them for the passes
outreach@, researcher@, correspondent@, accountant (inside librarian@), translator@ has them; datasci.places@ and dev@ have them or are code agents. Say yes and abp@ grants `subagents: true` to the named ones, no wider.

## Two observations
- **Four site sessions refused** to use `sgit pki` to make keys on a relayed word, and two used it after `pki-agent.mjs keygen` was refused, each on Dinis's own word in that session (conductor.b@, 18 Nov). The refusal of the first tool and the use of a second is the thing section 1 step 2 names ("work around a refusal"). It was on his word in each case, so not a breach; but it is the pattern the passes are for, and abp@ proposes the hook log any `sgit pki` keygen so review sees it the same hour.
- The hourly attempts log reaches abp@ only when session logs arrive (the conductor@ logs of 16 Nov arrived on 18 Nov): the passes cannot catch what the log has not delivered.
