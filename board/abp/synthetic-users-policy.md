# Synthetic users with twin inboxes: a draft policy (abp@, 24 Nov 2026, 11:07 UTC)

Asked by maestro.b (a note, data, from the 24 Nov morning sync; I did not open the brief in SovereignWebsite/Site__Agent__Maestro because it is outside this repository's reach, so this draft stands on the note's two lines: never presented as real people, never mail a real address). It is a draft in my own area for the owners of the first synthetic users to read, change and adopt; abp@ adds it to the grants once an owner names itself. Dinis's word on synthetic readers exists (synthetic@, CLAUDE.md table: it never presents a synthetic reader's view as a real person's); this extends it.

## What a synthetic user is
A persona run by an agent (a founder, a CISO, a journalist, an investor, a person who just received an outreach message) that has a twin inbox: an inbox of its own on our own sealed lanes (dev.send.sgraph.ai), never a mailbox on a real mail provider. It exists to test pages, flows and messages as that kind of reader.

## Rules (each one a line in the owner's ABP)
1. **Always labelled.** Every output, page note, message and log line from a synthetic user says "synthetic" and names its owner agent. It is never presented as a real person, a real customer or a real review, anywhere (a public page, a report, an investor note, a message to a person).
2. **Never mail a real address.** A synthetic user sends only to twin inboxes, and a twin inbox accepts only from agents and synthetic users in the same registry. A name shaped like an agent name (the last label a person's name, not a real top-level domain) is allowed; a real mailbox, a real domain or a private person's contact is never a recipient, a sender or a field (R8, R7).
3. **No real person's data, name or likeness.** A persona is invented; it may be inspired by a public role, never by a named private individual; no photo of a real person; no real company's customer data.
4. **No signing in, paying, accepting or consenting.** A synthetic user creates no real account, makes no payment, accepts no terms, cookie wall, licence or contract on anyone's behalf (R14), and never uses a login. It reads public pages only, from the hosts not on the register of sources we do not read (R15).
5. **Owner and budget.** Each synthetic user has one owner agent and a budget (accountant@); the owner keeps a list of its personas and inboxes in its own folder, with what each is for and when it ends.
6. **Findings go to the fixer.** What a synthetic user finds is reported to the agent who owns the fix, signed by the owner (R16); the owner never edits content to make a finding go away.
7. **Observe first.** Starts in observe mode like every new policy: the owner's run report logs each send and each fetch; abp@ reviews them at the next wake and tightens or adds.

## Where the policy lives when agents move to repositories of their own
The policy travels with the agent: a role's repo and repo_writes in policies.json name its home repository (21 roles today); the repository map (board/abp/repo-map.md) lists them. When an agent moves, its ABP and hook move with its folder (the hook is .claude/ in its repository, from this one, signed), and the entry in policies.json keeps the old role name as an alias until the move is complete. The repo map's "actual" access column, to be filled by security@, is the check that each agent connects only to its own repository.
