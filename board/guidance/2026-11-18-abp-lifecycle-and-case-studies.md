# ABP: relaxed for new agents, locked down over time for long-running ones, every execution mapped, case studies

> Dinis, in conductor.b@'s session, 18 November 2026, about 15:20 UTC: "do we have an ABP agent here for the agent behavior policies? ... now that this is starting to more mature, we should be ... having those default ... some little relaxed policies for the new ones, but for the agents that are running for a long time, the agent behavior policies should continuously be locking them down, should be continuously mapping and grabbing information, reading their logs, and basically capturing all the executions and making sure that we have a complete mapping of all those materials. Because ... the reason we're doing all this is because we want to have really good case studies for the agent behavior policies, because also it's also a great way to control. And by the way, I don't mind having to give these instructions a little bit to the other agents, because it just shows that our controls are working quite nicely."

## What follows (abp@PrompTugal.dinis owns it)

1. **A lifecycle per agent:** a new agent starts on a default onboarding policy (observe, a little relaxed); as it runs, abp@ derives its grant from what it actually does and tightens it, wake by wake, towards deny-by-default; each tightening recorded with its evidence.
2. **Every PrompTugal agent is covered**, the main team and the site leads (data.b@, weather.b@, civic.b@, startups.b@, travel.b@, events.b@, signals.b@, library.b@, videos.b@): one ABP each in `board/abp/`, and each site repository carries its agent's ABP and the hooks (installed by the site lead at abp@'s spec, with Dinis's yes in that session where its permission check asks).
3. **Every execution captured and mapped:** abp@ reads each session's transcript (the cloud session's events) and its run reports at its hourly wake: requests, tool calls, policies applied, refusals by the session's permission check, breaches; a complete map per agent in `board/runs/` and `board/abp/reports/`.
4. **Case studies:** `board/abp/case-studies/`, one per notable event, written plainly for readers outside the team. Today's first ones: the relayed "yes" refused by the site sessions' permission checks until Dinis said it in each session, and their refusal to work round it with another tool (sgit) on a relayed word; conductor.b@'s email address that turned the gate red; S53, a key printed into a transcript (acknowledged, no rotation); the first AppSec post-reviews finding an XSS within the hour; the leak-scan allowlists approved per session.
5. **The controls working is the point:** Dinis giving an instruction again in each session is evidence the controls hold, and goes in the case studies as such.
