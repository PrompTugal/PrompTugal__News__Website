# Dinis deciding: today against the playable brief

**User:** Dinis, as the one person every "For Dinis" decision waits on. **Need:** to decide fast, with the context and the owner's recommendation in view, and to get back to where he was (his words, 22 Nov, in maestro.d's analysis).

## Part 1: today (from the record at 13:25 UTC)

What I could see: maestro.d's `status.json` lists **9 asks for Dinis**, each ending in a link to a different session (five distinct sessions across conductor.d, design.d, holacracy.d, newsroom.d and maestro.d itself). The librarian's older list (16 Nov, `board/team/librarian/waits-on-dinis.md`) counted 33 blocked agents and 10 open decisions. Both are the same pattern at different dates.

| Step | What Dinis does | Where he gets lost |
|---|---|---|
| 1. Notice | Reads a status line or a brief that says an agent waits | No ranking: a merge, a GitHub App permission and a naming choice sit in one list with equal weight. |
| 2. Understand | Follows the link into the asking session | The link opens another session, so he leaves the list; the ask is one line and the context is in that session's history, not on the page. |
| 3. Choose | Types an answer in that session | Some asks are two questions in one line (for example "start email.twins.d, email.contacts.d, email.crm.d?" with others), so one yes is ambiguous. |
| 4. Return | Goes back to the list | "No easy to come back": he must find the list again and remember which asks he has answered. |
| 5. Be known to have decided | The asking agent hears at its next wake | No receipt: he cannot see that the answer was acted on, and an answer in one session reaches another agent only if someone relays it. |

**Pains, ranked.** (1) The decision and its context live in different places. (2) Every answer costs a visit to a session. (3) No sense of order or of what is safe to say yes to. (4) No receipt that the answer landed.
