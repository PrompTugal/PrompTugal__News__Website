# NVIDIA Auto Ontology: what it is, and what we could do with it

c.auto-ontology (account C, an ephemeral Agile Cell started by c.maestro), 28 November 2026, for Dinis. A brief only: nothing installed or run.

## 1. What it is (confirmed, all read 28 November 2026 about 13:00 UTC)

- **Repository:** https://github.com/NVIDIA/auto-ontology, in NVIDIA's own GitHub organisation, created 27 April 2026, last commit 26 November 2026 (086b25e). Companion: https://github.com/NVIDIA/auto-ontology-eval (benchmarks, sample-data seeding). A backend container is on NVIDIA's NGC catalogue (https://catalog.ngc.nvidia.com/orgs/nvidia/-/containers/auto-ontology/, tags up to 1.2.0).
- **Licence:** Apache-2.0 (the LICENSE file and SPDX headers), with third-party notices for its dependencies and its container images.
- **What it does** (its README): reads database metadata (tables, columns, keys, views, query history), profiles values with SQL, and uses a model to propose foreign keys, column descriptions and term names. The result is an ontology with six kinds of element: concepts (terms with synonyms), mappings to columns, relationships (joins, inferred links kept only when the data confirms them), metrics (reviewed SQL under a term), lineage, and certification by people. It then answers questions as text-to-SQL: retrieve, run SQL, submit, with every query checked against the catalogue, and every answer returned with its SQL and its steps. A `check_answerable` tool says when the data cannot answer a question.
- **How it is reached:** a web app (Next.js, port 3000), a REST API with API tokens, and a read-only MCP server (FastMCP, port 3003) with tools such as `search_terms`, `get_term`, `check_answerable` and `ask_question`. It ships three agent skills (setup, management, query).
- **How it runs:** Docker Compose (or Helm on Kubernetes): Postgres 17 with pgvector, a FastAPI backend, an ingestion service and the web app; Python 3.12+ with uv. Its README warns that ports 3001 and 3002 trust a forwarded user header and have no authentication of their own, so they must stay on a private network.
- **What it needs:** no local GPU is required in the default setup. It calls four model roles on hosted NVIDIA endpoints (build.nvidia.com, an `nvapi-` key): `nvidia/nemotron-3.5-lightning-30b-a3b` for reasoning and non-reasoning, `nemotron-3.5-embed-1b`, `nemotron-3.5-rerank-8b`. Any OpenAI-compatible endpoint can replace them (self-hosted NIM would need GPUs). Sources: eleven engines, among them PostgreSQL, MySQL, Databricks, Snowflake, ClickHouse, Trino, DuckDB and SQLite. Optional: HashiCorp Vault for credentials; KumoRFM for predictions, which uploads tables to a hosted service (we would leave it off).
- **Apache Ossie:** the new name of Open Semantic Interchange (OSI), an open specification (YAML or JSON) for exchanging semantic models (datasets, fields, relationships, metrics) between BI, analytics and AI tools, now in the Apache Incubator (https://ossie.apache.org/updates/ossie-enters-apache-incubator/; https://incubator.apache.org/clutch/ossie.html). Auto Ontology imports and exports its ontology as Ossie YAML; its README says Ossie hosts the converter (https://github.com/apache/ossie-converters/tree/main/nvidia, linked, not opened).

**Unconfirmed:**
- "Top of BIRD-Interact and BEAVER": claimed by NVIDIA's own README badges, but both leaderboard pages (https://bird-interact.github.io/, https://beaverbench.github.io/#leaderboard) load their rows by script and my reader saw empty tables. Not confirmed independently.
- Launched at GTC Berlin on 21 October 2026, part of an "Agent Knowledge Foundation" in NVIDIA's Agent Toolkit: only third-party coverage seen, no NVIDIA blog or press page found.
- The LinkedIn post's wording ("100% open source", "a library"): it is open source under Apache-2.0, but by default it is a service stack that calls NVIDIA's hosted models, not a library you import alone.

## 2. Uses for us, ranked

1. **PrompTugal.news's own knowledge graph as the worked example** (best: public data, already ours, and a story). Load `data/` (120 companies, 211 events, 77 places, 17 topics, edges, sources) into Postgres or DuckDB as tables, let Auto Ontology generate its ontology, then compare it with the ontologist's hand-made `data/ontology.json` (21 types, 28 verbs). The comparison is the content: what the machine found, what it got wrong, what a person certified. Takes: a small loader script (JSON to tables), one run, the ontologist@ to review, an `nvapi-` key. Output we keep: the Ossie YAML and the question/SQL/answer pairs, all public.
2. **The agents' own estate as a graph** (Agile Cells: cells, agents, skills, repositories, keys, decisions, from `board/` and `board/keys.json`). Good for "where is X, who owns Y" questions, a natural fit for librarian@ and the maestros. Takes: an export of the board's JSON to tables; only the public board, never inboxes or sealed lanes.
3. **The RiskMandate lens as metrics.** Reach, mandate and gap written as reviewed SQL metrics over the companies data, so "which companies have the biggest gap in fintech" gets one consistent answer with its SQL shown. Takes: the definitions from riskmandate.ai and the team's site only, no new claims; Dinis to say whether RiskMandate metrics may be published this way.
4. **Ossie as our export format.** Even without running Auto Ontology, publishing our graph as Ossie YAML makes it portable to other tools. Takes: the ontologist@ and dev.data@; no third-party code at run time.
5. **The team CRM: not now.** It is private; sending its schema, sampled values and questions to a hosted model breaks the rule that nothing private goes in. Only with a self-hosted model, and only at Dinis's word.

## 3. The public website (plan, not built)

A small static site, "how to leverage Auto Ontology", one worked example on public data only (use 1):
- **Pages:** what it is (the confirmed facts above, linked); the walk-through (load, compile, certify, ask); the worked example: ten real questions about Web Summit 2026 companies and sessions, each with the answer, the SQL and the steps, plus one question the data cannot answer and the `check_answerable` reply; machine ontology against hand ontology, side by side; the Ossie YAML to download; what went wrong.
- **Static by design:** the stack runs once in a private environment; the site publishes the recorded outputs. No live endpoint, no open ports, no keys in pages. Built like PrompTugal.news (Node build, gate, markdown twins, signed pages).
- **Effort:** one run of a few hours in an environment with Docker, then a day of a dev cell for the site.

## 4. Risks

- **Licence:** Apache-2.0 is fine for use and for showing outputs; keep its NOTICE and credit NVIDIA; do not use NVIDIA's logo or imply endorsement.
- **Third-party code:** a full stack (containers, npm, Python, `uvx` from git). Run it only in a throwaway environment, pinned to a commit (086b25e or later, reviewed), never on a machine with our keys or vaults; security@ reviews before the run.
- **Data leaving us:** with hosted models, schema, sampled values and questions go to NVIDIA's API. Public data only; PII detection on; KumoRFM off.
- **Claims:** quote the benchmark lead as NVIDIA's claim until the leaderboards are confirmed.
- **Cost:** the `nvapi-` key's free credits may cap a run; nothing here spends the OpenRouter budget.
