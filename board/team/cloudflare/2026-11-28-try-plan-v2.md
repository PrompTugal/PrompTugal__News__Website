## 1. "3 images: per IP, per account or per user?"

**Plain answer:** it is per **visitor**, as counted by our own code. Cloudflare only limits the whole account.

| Layer | Who sets it | Unit | What happens at the limit |
|---|---|---|---|
| Workers AI free allocation: 10,000 neurons a day | Cloudflare | **per Cloudflare account**, shared by everything in it (my reading of "everyone gets 10,000 Neurons per day", developers.cloudflare.com/workers-ai/platform/pricing/) | On Workers Free, calls fail until 00:00 UTC. On Paid, it bills $0.011 per 1,000 neurons |
| Workers Free: 100,000 requests a day | Cloudflare | per account | requests fail |
| **3 images a visitor a day** | **us** (a Durable Object counter) | per "visitor", defined below | we refuse with "come back tomorrow" (later: "top up") |
| **Daily cap per provider** (for example 150 images or $5) | **us** (one global Durable Object per provider) | per provider | we refuse everyone for that provider |

Who a "visitor" is decides how hard the counter is to cheat:

| Visitor = | How | Abuse risk | Friction |
|---|---|---|---|
| IP address | read the `CF-Connecting-IP` header | High and unfair: a VPN or a phone network resets it, and an office or a university shares one. Cloudflare's own rate-limit docs advise against keying on IP | none |
| Browser key or cookie | a random id we sign and set on the first visit | High: clearing the cookie or opening a private window gives 3 more | none |
| Turnstile + cookie | a token checked at the edge on every call (300 s, single use) | Medium: it stops scripts, not a patient person. **This is the minimum for a public free try** | almost none |
| Signed-in account | a magic link to an email, GitHub, or one of our vault identities; we issue a short-lived signed token | Low: one quota per verified identity, and throwaway emails are the main hole. **This is required for anything paid** | a sign-in step |

**Recommendation:** for the anonymous try, use Turnstile plus a signed cookie, 3 a day per cookie, with a second, looser count per IP (for example 20 a day) as a backstop, under the per-provider caps. After sign-in, the quota follows the account, which is also where pay-as-you-go balances live.

## 2. Plan v2: one service, several providers

**Shape:** one Worker, `try`, with one API and a provider behind each route. Everything is server-side: keys are Worker secrets and never reach the browser.

- `POST /v1/image` with `{prompt, provider?, size?}` uses Workers AI (flux-1-schnell, default and free), Higgsfield, or OpenRouter image models.
- `POST /v1/chat` (basic inference) uses Workers AI small models (default, free), OpenRouter, or AWS Bedrock.
- `GET /v1/me` returns the remaining quota and, later, the balance.
- OpenRouter goes through the AI Gateway (supported, confirmed), for logs, caching and cost analytics. The AI Gateway has no spend cap, so our own cap applies.

**Controls, all in our code:**
1. **Gate:** Turnstile on every call from the browser; a signed user token once sign-in exists.
2. **Quota per visitor** (a Durable Object keyed by the visitor id): images and chat turns a day.
3. **Spend cap per provider** (one Durable Object per provider): an estimated cost is reserved before the call and settled after, and the provider is refused once the day's or month's cap is reached. Providers' own prepaid limits sit underneath (Higgsfield prepaid balance **(unconfirmed details)**, OpenRouter credit limit, an AWS Budgets alert for Bedrock **(an alert, not a hard stop; unconfirmed)**).
4. **Kill switch:** a KV flag per provider and one for everything.
5. **Metering ledger per user** (D1): each call is a row with user, provider, model, units and estimated cost. No prompt text by default. This is what pay-as-you-go top-up will read later: a balance becomes a column, and the quota check becomes a balance check.
6. **Prices:** a table of our cost and our price per unit per provider, kept in the repository, so the margin is visible before anything is sold.

**Payment route (Dinis's decision, not built now):** for example Stripe Checkout for top-ups, credited by a webhook to the ledger. Alternatively, a merchant of record (for example Paddle or Lemon Squeezy, names (domain) not checked) that handles EU VAT. Selling keys to customers stays out of scope, as Dinis said.

**Lock-in kept thin:** provider adapters are plain functions behind one interface, and the ledger is SQL that can be exported. Only the counters and caps use Durable Objects.

## 3. First experiment (once the account and token exist, and Dinis says go here)

**Experiment 1, "free image, capped":** the `try` Worker on Workers **Free**, `/v1/image` with Workers AI flux-1-schnell only, Turnstile plus cookie, 3 a visitor a day, 150 a day globally, and the ledger in D1. A small "try an infographic" box on one PrompTugal.news page. We measure visitors, images, how many hit the 3-a-day wall (the traction signal for paying), and abuse attempts. Cost: zero, because Free fails at the limit. It runs for a week.

**Then, one at a time, each with its own cap set before its key goes in:** experiment 2 adds OpenRouter through the AI Gateway (chat plus better images); experiment 3 adds Higgsfield images; experiment 4 adds Bedrock; experiment 5 adds sign-in plus top-up, after the payment decision. Moving to Workers Paid ($5 a month) only when Free's limits bind, because Paid removes the free plan's hard stop.
