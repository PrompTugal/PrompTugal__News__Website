## What I learnt

1. **A limit tuned on this morning's data was wrong by the afternoon.** At 06:00 a good deploy took 7 to 12 s and a stuck one never finished, so I cut the deploy limit to 2 minutes. By 14:00 Pages queued deployments for minutes, and my limit cancelled them while queued: the site fell behind from 14:20 to 16:16 (5 of 46 runs green). Measure the last hour before changing a limit.
2. **Pages names a deployment after the commit.** A run cannot deploy its commit twice after a timeout; a refusal ("due to in progress deployment") creates no deployment and can be retried.
3. **`deploy-pages` cancels its own deployment when it times out**, and a cancelled deployment is not served.
4. **Push the release commit and its tag together** (`git push --atomic`): GitHub once took the branch and refused the tag after it, and the deploy never ran (v0.1.176, v0.1.188 are on dev untagged).
5. **One deployment per burst is what Pages can take.** A run that is no longer the branch's head now skips its deploy; the newer run deploys everything.
6. **A dispatched redeploy is only worth it when nobody pushed after.** At one push a minute, dispatches only filled Pages' queue.
7. **The GitHub status page said "operational" all afternoon.** Our own volume is the load.
