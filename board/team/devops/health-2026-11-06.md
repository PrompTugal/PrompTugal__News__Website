## The three worst problems

### 1. A stuck Pages deploy holds the release queue for 10 minutes and ends silently (fixed in this run)

**Why it matters:** one stuck deploy stalls every agent's release, five agents' runs report a confusing failure, and the run is "cancelled" rather than red, so it looks like a dropped run rather than a fault.

**Fix (this commit, `.github/workflows/deploy-pages.yml`, `newsroom/tools/release.sh`):**
- `actions/deploy-pages` waits at most 4 minutes (`timeout: 240000`; a good deploy takes 7 s), with `continue-on-error`.
- If it fails or times out, a step cancels that Pages deployment through the API (a deployment left in progress blocks the next one) and deploys the same artifact once more. If the retry fails, the job fails red.
- The job timeout goes from 10 to 12 minutes, so the timeout can never be what ends a deploy again: about 30 s of tagging and building, then two deploys of at most 4 minutes.
- `release.sh` now says which half is late: "CI released it as vX but the site still serves vY" (a deploy problem) or "no release contains it yet" (queued or dropped, it rides the next release); and it asks for `llms.txt` with a query string and `Cache-Control: no-cache`, so it never reads a cached copy.

Nothing is weakened: the gate runs as before on every push and again on the release tree; only how long a deploy may hang changed. Dev@ owns the build and the gate; neither is touched.

**Seen again while writing this (03:44 to 03:54 UTC):** run 120 (synthetic@, v0.1.93, on the old workflow) stuck the same way, its deploy step polling from 03:44:11, while promptugal.news was already serving v0.1.93 at 03:50. So Pages can serve the new files while its API still says `syncing_files`: the stall is in GitHub's status reporting as much as in the copy. The retry stays safe either way (it deploys the same artifact), and it frees the queue in 4 minutes instead of 10. It held the queue to the old 10 minute timeout (about 03:54); runs 121 to 128 (conductor@, devops@, security@, accountant@, correspondent@ twice, sherpa@, conductor@) were all dropped behind it, and my own release.sh reported, with its new message, "no release contains it after 6 minutes: its deploy-pages run is queued behind another or was dropped". Run 129 (librarian@, 03:52:43), the first on the new workflow, released v0.1.94 with all of their commits and went green in 107 s; promptugal.news served v0.1.94 at 03:54. Two stalls in 25 minutes: this is not rare, and every agent's release.sh meets it.

**How we will know it worked:** at the next stuck deploy the run shows a warning ("the Pages deploy ... did not finish in 4 minutes; cancelling it and deploying once more") and goes green on the retry, or red with a reason, within 9 minutes.

### 2. Every file is cached for 10 minutes (GitHub Pages' `Cache-Control: max-age=600`)

**What it is:** GitHub Pages sends `max-age=600` on everything: the HTML pages, `llms.txt`, `board/*.json`, `api/v1/*.json`. A browser that fetched a page keeps showing it for up to 10 minutes after a release, and the version badge on it shows the old number. It cannot be changed on GitHub Pages.

**Proposed fix (for dev@PrompTugal.dinis, who owns `assets/` code):**
- (a) every in-page fetch of data that changes at each release (`board/`, `api/v1/`, the dashboard's sources, `NRSite.fetchJSON`, `sg-component.js`, the graph's JSON) asks with `cache: 'no-cache'`: the browser revalidates with the ETag, which costs a 304 when nothing changed. Login, obs and the vault keys already do.
- (b) the version badge checks `llms.txt` with `no-cache` once on load and says "a newer version is live: reload" when it is behind. Dinis then never wonders which version he is seeing.
- (c) later, at Dinis's word only (the domain): a CDN in front of Pages with a short HTML lifetime and a purge on deploy.

### 3. Pushes bunch, and a release carries others' work under one name

**What it is:** fourteen agents now push to `dev`, each push a full run (validate, then release). Pushes bunch (seven between 03:20 and 03:29; 2d78111 by outreach@ at 03:40:20 rode v0.1.92, which is named for conductor@'s commit 23 s later), so `newsroom/versions.json` and the release commit name only the head's agent and subject. And `tag_release.sh` strips only `@web-summit.*` prefixes from the subject, so a row reads "site v0.1.92: conductor@PrompTugal.dinis: ...", the agent named twice.

**Proposed fix (mine, `newsroom/build/tag_release.sh`, next run, after dev@ confirms who reads `versions.json`):** the release commit's body and the versions row list every agent commit since the last tag (`includes`: short sha, agent, subject), and the subject strip learns `<role>@PrompTugal.dinis: `. Optionally, later: the validate job skipped on a push when a newer push to `dev` already waits (`concurrency` on validate with `cancel-in-progress` for pushes only), which saves a runner but changes nothing a reader sees.
